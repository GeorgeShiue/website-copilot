### Slide 4：專案背景 · 1.5 分鐘（1:30–3:00）

#### 口頭要點

- 網站資訊量持續成長，但搜尋體驗沒有同步進化——FAQ、部落格、多層級頁面分散各處
- 即使找到說明文字，使用者仍須自行理解並操作，過程中容易迷失或出錯
- 這不是單一網站的問題，而是「複雜網站」的普遍困境

#### 口頭補充（來源有、簡報上無）

- 以實驗室網站為例：招生公告、論文發表、成員資訊分散在不同頁面，使用者想問「教授還有收碩士生嗎？實驗室近期研究方向是什麼？」需要自己跨頁面拼湊
- 現代 SPA（單頁應用程式）的動態渲染特性讓傳統搜尋引擎更難索引

---

### Slide 5：競品分析 · 2.5 分鐘（3:00–5:30）

#### 口頭要點

- **AI 客服**（Zendesk AI、Intercom Fin AI）：
  - 已從關鍵字決策樹進化到 LLM 驅動的自主代理
  - 能回答問題、附來源、甚至串 API 執行退款／查物流
  - 但本質上還是「唯讀」——不能操作網站介面、不能幫使用者點按鈕或跳轉頁面
- **AI Web Agent**（Browser Use、Skyvern、LaVague）：
  - 開源框架，能自主操作瀏覽器：填表單、跨頁面點擊、視覺辨識 UI
  - 但依賴即時感知（每次互動都要重新解析 DOM 或截圖），缺乏對網站的預先理解
  - 成本高、延遲高、每次互動都像「盲人摸象」
- **AI 瀏覽器**（Gemini in Chrome、Edge Copilot、Perplexity Comet）：
  - 內建瀏覽器的 AI 助理，有跨分頁理解、背景自動化能力
  - 通用型設計，不會針對個別網站深度整合
  - 每次仍需處理完整頁面 DOM 或截圖，延遲與成本仍高

#### 口頭補充（來源有、簡報上無）

- Browser Use 已在 GitHub 突破 100k Stars，底層導入 Rust 核心，效能極佳
- Skyvern 完全放棄 DOM 解析，改用 Set-of-Marks 視覺標註——在互動元素上畫數字標籤讓 AI 「看圖操作」
- LaVague 利用 RAG 技術過濾 HTML 區塊，只餵相關片段給 LLM，解決 DOM 過大的 Token 成本問題——這和我們 Phase 1 的技術思路一致
- 這三類競品共同的盲點：沒有人「預先讀懂網站」，每次都要從零開始感知

### Slide 6：痛點分析 · 1.5 分鐘（5:30–7:00）

#### 口頭要點

- **痛點① 僅止口頭說明**：
  - AI 客服只能給你文字步驟，你得自己去頁面上找按鈕、填表單
  - 原因：資安考量（XSS 風險）→ 市售產品普遍採唯讀策略；SPA 動態渲染 → 外部代理難以精準定位 UI 元件
- **痛點② 缺乏事先理解**：
  - Web Agent 每次都重新解析 DOM／截圖，沒有全局知識地圖
  - 結果：高延遲、高 Token 成本、無法理解頁面之間的業務邏輯關聯
- **痛點③ 不支援長期互動**：
  - 對話一拉長，歷史訊息堆積 → 模型注意力稀釋、上下文污染、遺忘中段（Lost in the Middle）
  - 缺乏結構化狀態追蹤——無法分辨哪些任務已完成、哪些還在進行

#### 口頭補充（來源有、簡報上無）

- 痛點② 的比喻：就像沒有地圖的導航系統，只能看到眼前 50 公尺，無法規劃全局路線
- 痛點③ 的具體場景：使用者在同一對話中交替提出多個不相關需求，或反覆修改同一設定——模型難以區分「已完成的子任務」和「進行中的目標」，最終產生幻覺
- 這三個痛點直接對應我們的三階段開發規劃

### Slide 8：專案目標 · 1.5 分鐘（7:30–9:00）

#### 口頭要點

- 三大目標，每一個對應一個痛點：
  1. **預建網站知識庫** → 解決「缺乏事先理解」（痛點②）：事先爬取、索引全站，建立完整知識地圖
  2. **賦予網站操作能力** → 解決「僅止口頭說明」（痛點①）：不只是回答問題，而是代為執行操作
  3. **導入對話狀態管理** → 解決「不支援長期互動」（痛點③）：Session 分割、上下文壓縮、摘要遞迴

#### 口頭補充（來源有、簡報上無）

- 目標① 的核心思路：將「即時畫面感知」與「預建知識庫」解耦——導入網站前先建好知識地圖，執行期間只需輕量級感知當前 URL 或前端狀態，就能精準調用先驗知識
- 目標② 的技術手段：封裝底層 API 為標準 MCP 工具，讓 Agent 能自主發送 HTTP 請求進行狀態變更，而非僅在前端模擬點擊
- 目標③ 的設計：每個 Session 有明確目標、狀態與生命週期；歷史操作日誌壓縮為結構化意圖狀態，捨棄失效資訊

### Slide 9：技術分析 · 1.5 分鐘（9:00–10:30）

#### 口頭要點

- 借鏡 GitHub Copilot 的四大技術面向——業界最成熟的 AI 編碼助手架構：
  1. **全站知識索引 & 檢索**：類比 GitHub 全域代碼搜尋引擎 Blackbird + 本地向量索引
  2. **網站操作介面**：類比 Copilot 的 MCP 開放標準協定——統一包裝網站工具供 AI 調用
  3. **代理自動化**：類比 Copilot 的背景智囊模式——任務拆解、非同步執行、錯誤自癒
  4. **對話狀態管理**：類比 Copilot 的 Jaccard 相似度演算法——監聽前端狀態、動態壓縮上下文

#### 口頭補充（來源有、簡報上無）

- MCP（Model Context Protocol）是關鍵技術——它讓 AI 能跨越編輯器調用終端機、編譯器等外部工具。我們將同樣的概念用在網站操作上，把 CMS API、會員系統包裝為 MCP Server
- 技術架構的三層設計：
  - 層一：全站知識庫與語義索引管線（Phase 1 核心）
  - 層二：Agent 推理核心與工具調用機制（Phase 2 核心，ReAct 雙引擎：大腦規劃 + 手腳執行）
  - 層三：前端感知層與對話狀態管理（Phase 3 核心）

### Slide 12：模組工作流 · 1.5 分鐘（12:30–14:00）

#### 口頭要點

- 三階段 pipeline 依序串接：爬取網站 → 摘要圖片 → 建置向量索引
- 每階段的輸出即下一階段的輸入，形成一條龍自動化
- 可獨立執行單一模組（方便 debug 與實驗），也可全流程自動串接

#### 口頭補充（來源有、簡報上無）

- Workflow 層的設計責任是「編排與執行」，不直接手寫設定——各模組的 config 由 `app/configs/` 統一管理
- RunManager 負責每次執行的輸出目錄管理：`runs/<timestamp>/<module>/<run>/`，包括 `results.json`、`module_config.toml`、`terminal.log`，方便回溯實驗
- CLI 入口透過 `cli.py` 提供四個指令：`crawl-cli`、`summarize-cli`、`rag-build-cli`、`rag-query-cli`
- 也可以直接用 `main.py` 程式呼叫，從爬蟲一路串接到圖片摘要

### Slide 13：模組一 — Website Crawler · 1.5 分鐘（14:00–15:30）

#### 口頭要點

- 非同步爬取，限制網域、深度、頁數上限，避免失控
- HTML → Markdown 轉換，自動移除導覽列、頁尾等雜訊，保留純淨內文與圖片連結
- 平行處理多個請求，內建去重機制與統計記錄（成功／錯誤／重複頁面數）

#### 口頭補充（來源有、簡報上無）

- 底層使用 `crawl4ai` 套件進行爬取與 Markdown 生成，搭配 `mdformat` 格式化輸出
- 設定檔位於 `configs/website_crawler/{name}.toml`，支援不同網站切換不同設定
- 輸出以頁面標題作為 Markdown 檔名，附帶來源網址 metadata，為後續 citation 鋪路
- 已知限制：HTML 還可包含更多結構化資訊（如表格語意），未來考慮爬取網站地圖或直接讀取後端資料庫

### Slide 14：模組二 — Image Summarizer · 1.5 分鐘（15:30–17:00）

#### 口頭要點

- 用 VLM（視覺語言模型）為每張圖片生成結構化文字描述
- 摘要結果回寫至 Markdown，讓純文字向量資料庫也能「看到」圖片內容
- Prompt 迭代歷程：v1（基礎描述）→ v2（優化結構）→ v3（可驗證摘要）
- 內建圖片下載快取、失敗自動重試（指數退避 + jitter）

#### 口頭補充（來源有、簡報上無）

- 這是一種「降維打擊」策略：用 VLM 把圖片轉成文字，無需改動底層向量資料庫架構，就能讓純文字檢索具備圖片感知能力
- 支援兩種圖片來源模式：從 Markdown 標記擷取、或從爬蟲結果的 images 欄位直接取用
- 使用 `litellm` 作為 LLM 抽象層，可靈活切換 Gemini／GPT 系列模型
- 快取鍵為圖片 URL，避免重複下載與重複摘要，節省 API 成本
- 已知限制：圖片摘要可能喪失細部資訊——未來考慮多模態 RAG 或讓 Agent 動態查找原始圖片
- 未來還需處理表格與 PDF 文件等多元資料格式

### Slide 15：模組三 — RAG · 1.5 分鐘（17:00–18:30）

#### 口頭要點

- 解析 Markdown → 語意切塊 → 向量嵌入 → 存入 Qdrant → 語意檢索 → LLM 生成回答
- 使用 `MarkdownHeadingMergeParser` 合併空標題，保留標題路徑確保切塊語意完整
- Embedding 使用 OpenAI `text-embedding-3-small`，向量資料庫使用 Qdrant 本地持久化
- 查詢引擎支援相似度門檻過濾（`SimilarityPostprocessor`），排除不相關節點
- 支援增量載入既有 Qdrant 儲存，不需每次重建索引

#### 口頭補充（來源有、簡報上無）

- 切塊參數 `chunk_size=800`、`chunk_overlap=100`，目前表現最平衡
- 查詢 LLM 使用 `gemini-3.1-flash-lite`（經實驗驗證性價比最高）
- 評估使用 FaithfulnessEvaluator + RelevancyEvaluator，搭配獨立 evaluator LLM（`gpt-5.4`）
- 整個 RAG 管線以 LlamaIndex 框架為基礎搭建
- Workflow 提供 `run_rag_build()`（首次建置）和 `run_rag_query()`（重複查詢 + 評估）兩種入口
- API key 依用途分三組獨立環境變數：Embedding、Query Engine、Evaluator，避免混淆

### Slide 16：網頁資料處理設計 · 1.5 分鐘（18:30–20:00）

#### 口頭要點

- **HTML → Markdown**：爬取後轉換、移除雜訊，保留內文與圖片連結
- **空標題合併**：`MarkdownHeadingMergeParser` 將孤立標題併入下一個有實質內容的節點，避免切出無效 Chunk（例如只有 "## 簡介" 但沒有內文的節點）
- **Metadata 抽離**：圖片連結、來源網址等非文字資訊放入 Metadata，避免汙染向量空間，同時保留 citation 追溯能力

#### 口頭補充（來源有、簡報上無）

- Metadata 策略是精心設計的：`page_title` + `page_url` 放在 metadata，圖片連結抽到 `metadata["images"]`——這些資訊不需要被向量化比對，但必須保留供回答生成時引用
- `SentenceSplitter` 使用 `paragraph_separator="\n\n"` 確保段落邊界不被切斷
- 自訂 `MarkdownImageExtractor` 將圖片標記替換為 alt 文字，讓圖片摘要、OCR、頁面關聯保留在同一 Node 中

### Slide 18：實驗設計 · 1.5 分鐘（20:30–22:00）

#### 口頭要點

- 5 題測試問題，涵蓋三種問題類型——不是隨便挑題目，而是刻意設計來測試不同能力維度
- 測試配置：`top_k=5, cutoff=0.45, gemini-3.1-flash-lite`（都是經過前期參數實驗確定的最佳值）
- 每題 10 次 query，共 50 次，用 FaithfulnessEvaluator + RelevancyEvaluator 雙指標評估
- 資料來源：同一份 vector store（`data/webpages/prompt-v3`），確保比較基礎一致

#### 口頭補充（來源有、簡報上無）

- 前期進行了兩組實驗來確定最佳參數：
  - **查詢模組設定實驗**：比較不同 `top_k`（2/5/10）和不同 `cutoff`（0.4/0.45/0.6），確定 `top_k=5, cutoff=0.45` 為最佳平衡
  - **語言模型實驗**：比較 4 個 Gemini 模型（flash-lite / flash-preview / 3.5-flash / 2.5-pro），結論是 `gemini-3.1-flash-lite` 在所有題型上 Relevancy 最高（100%）且 Latency 最短（59s avg）——更強的模型反而更慢且更不準確，因為檢索瓶頸抵消了模型能力優勢
- 三種問題類型：
  - 指引型：有明確、可驗證的答案（如「加入實驗室需要哪些資料」）
  - 時間範圍型：查詢包含時間限制（如「近三年發表論文」）
  - 名單型：期望回答一個列舉列表（如「實驗室成員有哪些人」）

---

### Slide 19：實驗記錄 · 2 分鐘（22:00–24:00）

#### 口頭要點

- **指引型**（加入實驗室所需資料、如何聯絡教授）：
  - 穩定度 ✅ 100%，10 次測試 Faithfulness / Relevancy 全數通過
  - 有明確且一致的來源支撐（Prospective_Students 頁面），現有配置即可穩定處理
- **時間範圍型**（近三年發表論文、2024 年活動）：
  - 穩定度 ❌ 最不穩定
  - 核心問題：查詢中的「近三年」未被轉為明確年份，檢索時混入最新消息、活動公告、學位論文等不同頁型
  - 即使手動改成明確年份（如「2024-2026 年論文」），仍因頁型混雜而不穩定
- **名單型**（實驗室成員有哪些人）：
  - 穩定度 ❌ 檢索失靈
  - `Members.md` 始終未被 recall——原因是每筆成員資料夾帶大量 VLM 圖片描述（如「年輕男性身穿學位袍…」），embedding 語義被圖片描述主導，與查詢的語義距離過遠
  - 調大 `top_k` 或降低 `cutoff` 都無效——這是純向量檢索對結構化列表的本質局限

#### 口頭補充（來源有、簡報上無）

- 名單型的次生問題：當檢索不到正確來源時，LLM 會從公告頁面中擷取零散人名，外推為一份「看似完整」的成員名單——這是生成層的過度推論
- 時間範圍型的診斷：單純調整 `top_k` 或 `llm_name` 無法根本解決——需要 query rewrite（將「近三年」轉為 `2024–2026`）+ page_type routing（區分論文頁 vs 新聞頁 vs 活動頁）
- 指引型不需任何改動，維持現有配置即可

### Slide 20：實驗總結 · 2 分鐘（24:00–26:00）

#### 口頭要點

- **核心洞察**：RAG 的瓶頸不是單一參數可以解決的——是「檢索精準度 × 檢索召回率 × 生成約束」三者的平衡取捨。`cutoff` 太高 → 召回不足的查詢變 Empty Response；`cutoff` 太低 → 噪音混入引發過度推論
- 不同問題類型的脆弱點截然不同，需要差異化處理——不能一個設定打天下

#### 改善方向

1. **改善檢索**（P0 優先）：
   - 導入混合檢索（向量 Dense + BM25 關鍵字 Sparse）——解決名單型召回瓶頸
   - 查詢擴展（Query Expansion）或頁面類型路由（Page Type Routing）——解決時間範圍題的頁型混淆
2. **生成約束**（P1）：
   - 對名單型、時間範圍類查詢強制要求來源追溯標示（Provenance），避免模型過度推論
3. **閾值彈性化**（P2）：
   - 保留 `cutoff=0.45` 為預設；對低召回題型加入動態降閾或 fallback 備援機制

#### 口頭補充（來源有、簡報上無）

- 混合檢索的具體做法：向量檢查找「語義相似」的內容，BM25 找「關鍵字精準匹配」的內容，兩者加權融合後排序——這對名單型問題尤其關鍵，因為「成員」這個詞在 `Members.md` 中會反覆出現
- Page Type Routing 的思路：在爬取階段就為每個頁面標記類型（論文頁、公告頁、活動頁、成員頁），查詢時根據問題類型路由到對應頁面群——避免論文查詢混入活動公告
- 這些改善方向將在 Phase 1 收尾階段優先處理
